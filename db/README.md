# База данных РемКомСтрой

Реализация текущей [ER-модели](../docs/er/remkomstroy.drawio) для PostgreSQL **14 и новее**. Требуются клиент `psql` и доступ к серверу PostgreSQL. Имена таблиц и столбцов английские; их соответствие сущностям приведено ниже.

## Состав файлов

| Файл | Назначение |
|---|---|
| `001_schema.sql` | Таблицы, PK, FK, CHECK, UNIQUE, индексы и начальные роли |
| `002_integrity.sql` | Функции и триггеры целостности |
| `install.sql` | Последовательное подключение обоих файлов в существующей базе |
| `create_database.sql` | Создание отдельной базы и установка схемы |
| `drop_database.sql` | Удаление отдельной базы вместе со всеми её данными |
| `000_drop_schema.sql` | Удаление только схемы `remkomstroy` в текущей базе |
| `tests/integrity.sql` | Положительные и отрицательные проверки; тестовые записи откатываются |
| `tests/concurrency.py` | Проверка двух одновременных транзакций на создание цикла |

Скрипты запускаются через **psql**, поскольку установщик использует команды `\ir` и `\connect`. Все команды ниже приведены относительно корня репозитория. `-X` исключает влияние пользовательского `.psqlrc`. Хост, порт и пользователь задаются обычными параметрами `psql` или переменными `PGHOST`, `PGPORT`, `PGUSER`. Пароль можно передавать через `.pgpass`; в файлах проекта его нет.

## Создание отдельной базы

```bash
psql -X -d postgres -v db_name=remkomstroy -f db/create_database.sql
```

Для создания базы у подключающегося пользователя должно быть право `CREATEDB`. По умолчанию имя базы — `remkomstroy`; параметр `db_name` позволяет его изменить. База создаётся из `template0` с кодировкой UTF-8. Подключающийся пользователь становится её владельцем.

Скрипт откажется создавать уже существующую базу и не удаляет старые данные. Если база создана, но установка прервалась, ошибка будет показана, а база останется для диагностики. Исправление или удаление такой базы выполняется явно.

## Установка на Helios в существующую базу

Если используется предоставленная база `studs`, новую базу создавать не требуется:

```bash
psql -X -h pg -d studs -f db/install.sql
```

Если имя пользователя отличается от локального, добавьте `-U ваш_логин`. Все объекты проекта создаются в отдельной схеме `remkomstroy`. Нужны права на создание схемы в выбранной базе.

Для установки необходимы **оба** файла: `001_schema.sql` и `002_integrity.sql`. Используйте `install.sql`, чтобы не пропустить триггеры. Каждый из двух этапов установки выполняется в транзакции. Повторная установка поверх существующей схемы завершается ошибкой, без автоматического удаления данных.

## Удаление

Для удаления отдельной базы подключитесь к служебной базе, а не к удаляемой:

```bash
psql -X -d postgres -v db_name=remkomstroy -f db/drop_database.sql
```

Команда удаляет указанную базу целиком. Принудительное отключение других клиентов не используется: при активных подключениях удаление завершится ошибкой.

В `studs` удаляется только схема проекта:

```bash
psql -X -h pg -d studs -f db/000_drop_schema.sql
```

Этот скрипт удаляет схему `remkomstroy` со всеми её данными и зависимыми объектами; саму базу `studs` не удаляет. Для повторной установки после явного удаления снова выполните `install.sql`.

## Даталогическая модель

В ER-модели 13 сущностей. Реляционная модель содержит **17 таблиц**: 13 соответствуют сущностям и ещё 4 реализуют M:N.

| Сущность / связь | Таблица | Первичный ключ и основные ссылки |
|---|---|---|
| Пользователь | `app_users` | `id`; ФИО `full_name`, email `email` |
| Роль | `roles` | `id`; название `name` |
| Пользователь — Роль | `user_roles` | PK `(user_id, role_id)`; оба поля — FK |
| Подрядчик | `contractors` | `id`; название `company_name`, статус `status` |
| Представитель компании | `company_representatives` | PK/FK `user_id`, FK `contractor_id`, bool `is_primary` |
| Объект ремонта | `facilities` | `id`; название `name`, вид `kind`, адрес `address` |
| Элемент объекта | `facility_elements` | `id`; FK `facility_id`, необязательный `parent_id`; положение `location` |
| Вид работ | `work_types` | `id`, название `name` |
| Подрядчик — Вид работ | `contractor_work_types` | PK `(contractor_id, work_type_id)`; оба поля — FK |
| Проект ремонта | `repair_projects` | `id`; FK `element_id`, `author_id`; актуальная редакция `current_version` |
| Ремонтная работа | `repair_works` | `id`; FK `project_id`, `work_type_id`, `element_id`, необязательный `contractor_id` |
| Работа — Работа | `work_dependencies` | PK `(predecessor_id, successor_id)`; оба поля — FK на работы |
| Тендер | `tenders` | `id`; FK `project_id`; редакция `plan_version` |
| Тендер — Работа | `tender_works` | PK `(tender_id, work_id)`; оба поля — FK |
| Предложение | `bids` | `id`; FK `tender_id`, `contractor_id` |
| Запрос на изменение | `change_requests` | `id`; FK `source_work_id`, `element_id`, `author_id`, необязательный `expert_id` |
| Приёмка работы | `acceptances` | `id`; FK `work_id`, `expert_id` |

Точные типы, обязательность и все поля определены в `001_schema.sql`. Искусственные идентификаторы — `bigint GENERATED ALWAYS AS IDENTITY`, объёмы и деньги — `numeric`, даты — `date`, срок ответа на тендер — `timestamptz`. Дополнительные сущности старой схемы из 31 таблицы удалены из реализации: она заменена текущей компактной моделью. Это установка с нуля, а не миграция существующих данных.

### Представительство

Пользователь может существовать без компании. Компания может существовать без представителей. Одна компания имеет несколько представителей; пользователь представляет максимум одну компанию, поэтому `company_representatives.user_id` одновременно PK и FK.

`is_primary` — обязательный булевый флаг с умолчанием `false`. Наличие главного представителя и единственность главного не ограничиваются: эти правила не согласовывались. FK принадлежности компании в `app_users` и FK пользователя в `contractors` отсутствуют.

### Версии и зависимости

Код `work_code` уникален в паре проект/редакция: `UNIQUE(project_id, version_no, work_code)`. Одна логическая работа в разных редакциях может иметь одинаковый код. Зависимости разрешены только между работами одного проекта и одной редакции.

Версии остаются числовыми атрибутами. Не реализованы автоматическое копирование плана, перенос статусов и полноценная история его снимков. Проверка закрытия проекта рассматривает работы `current_version`; перевод редакции и её наполнение должны выполняться согласованной транзакцией.

## Целостность средствами DDL

- `PRIMARY KEY`, `NOT NULL` и `FOREIGN KEY` обеспечивают наличие идентификаторов и обязательных ссылок.
- Пустые названия и описания запрещены. Email проверяется на базовый формат и уникален без учёта регистра.
- Объём, цена, продолжительность и номера редакций положительны; гарантия неотрицательна. `NaN` запрещён для числовых объёма и цены.
- Значения статусов, приоритета и результата приёмки ограничены `CHECK`.
- Составной FK `(parent_id, facility_id)` не позволяет назначить родителя из другого объекта.
- Повторные пары M:N запрещены составными PK; зависимость работы от самой себя запрещена `CHECK`.
- Для компании в одном тендере хранится одно предложение. История его версий не реализована.
- Частичный уникальный индекс разрешает не более одного предложения-победителя в тендере. Победителю нужно место в рейтинге; при выборе места ниже первого нужно непустое обоснование.
- Решение по запросу требует эксперта и текста решения. Возврат на доработку требует замечаний и срока устранения не раньше даты проверки.
- Удаление объектов, на которые ссылаются проекты, работы и история, ограничено `RESTRICT`. Вспомогательные принадлежности пользователя и состав удаляемого тендера используют `CASCADE`.

Эти ограничения защищают данные; они не заменяют аутентификацию и проверку прав пользователя в приложении.

## Целостность средствами триггеров

`validate_structure()` проверяет итоговое состояние связанных данных при INSERT, UPDATE и DELETE:

1. В иерархии элементов нет циклов.
2. Элемент работы относится к тому же объекту, что и исходный элемент проекта. Проверяется также изменение проекта и самого элемента.
3. Назначенный подрядчик обладает требуемым видом работ; удаление используемой компетенции тоже запрещается.
4. Зависимости работ не образуют циклов и связывают один проект и редакцию.
5. Работы тендера принадлежат его проекту и редакции.
6. Затронутый элемент запроса принадлежит тому же объекту, что и исходная работа. Он может отличаться от элемента самой работы.
7. Выполнение, доработка и приёмка зависимой работы требуют успешной приёмки её предшественников. Перед добавлением новой блокирующей зависимости активную работу нужно приостановить (`PAUSED`).
8. У выполняемой работы есть подрядчик; статус `ACCEPTED` требует положительного результата последней зарегистрированной приёмки (по `id`). Старый успешный акт не позволяет обойти последующий возврат на доработку.
9. Проект нельзя завершить с незавершёнными работами актуальной редакции или вообще без работ в ней. Отменённые работы (`CANCELLED`) не блокируют закрытие.

Проверки оформлены как `CONSTRAINT TRIGGER DEFERRABLE INITIALLY IMMEDIATE`. Для согласованного изменения нескольких связанных строк их можно отложить до конца транзакции:

```sql
BEGIN ISOLATION LEVEL SERIALIZABLE;
SET CONSTRAINTS ALL DEFERRED;
-- Согласованные изменения состава, элементов и зависимостей.
COMMIT;
```

Для межтабличных изменений используйте `SERIALIZABLE` и повторяйте транзакцию при SQLSTATE `40001` или взаимоблокировке `40P01`. Триггер `lock_integrity_changes()` дополнительно сериализует изменения структурных таблиц транзакционной advisory-блокировкой. Её область — учебная система; это сознательное ограничение параллелизма. Проверки обходят текущие наборы данных, поэтому реализация рассчитана на небольшой объём курсовой, без заявления о производительности на больших графах. `REPEATABLE READ` для таких изменений не поддерживается как способ защиты от конкурентных изменений.

`check_acceptance()` разрешает добавлять приёмку только для работы `ON_ACCEPTANCE`. `apply_acceptance()` отражает результат в статусе работы (`ACCEPTED` или `REWORK`). Приёмки сохраняются как история: изменение и удаление записей запрещены. Повторная проверка — новая запись после повторной передачи работы в `ON_ACCEPTANCE`.

## Проверка

Запускайте на отдельной тестовой базе с установленными схемой и триггерами:

```bash
psql -X -d remkomstroy -f db/tests/integrity.sql
```

Проверки охватывают допустимые операции и ожидаемые ошибки DDL/триггеров. Тестовые данные создаются в транзакции и откатываются. Значения identity-последовательностей при откате могут увеличиться — для PostgreSQL это нормальное поведение.

Тест не является отдельным скриптом заполнения демонстрационными данными. Заполнение, процедуры критичных запросов и обоснование индексов — следующие пункты этапа 2, они не входят в этот запрос.

Для конкурентной проверки в отдельной тестовой базе (нужен Python 3):

```bash
PGDATABASE=remkomstroy python3 db/tests/concurrency.py
```

Тест создаёт временные записи в базе, проверяет две реальные сессии и удаляет свои записи после проверки. Хост, порт и пользователь также задаются переменными `PGHOST`, `PGPORT`, `PGUSER`.

Требования к созданию базы и синтаксис параметров проверены по документации PostgreSQL: [CREATE DATABASE](https://www.postgresql.org/docs/14/sql-createdatabase.html), [psql](https://www.postgresql.org/docs/14/app-psql.html).
